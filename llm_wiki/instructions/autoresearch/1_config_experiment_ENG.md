# Autoresearch — Experiment Configuration Commands

Now we need to handle the experiment configuration part, meaning the actual implementation of these 3 commands:

- `add` : used to configure the experiment. Note that this command does not create a copy of the experiment files but simply saves their path internally in the tool.
- `list` : to display all experiments in the registry (can be abbreviated as `ls`)
- `remove` : removes the specified experiment from the registry (can be abbreviated as `rm`)

---

# General Notes

An *experiment* refers to an iterative hyperparameter optimization process.
Since it is an iterative process, the same experiment can be run multiple times (`round`).

First of all, `autoresearch` will need something to keep track of all saved experiments.
You can use the same method used to keep track of backends — a sort of internal registry within the tool.
More information about the registry at the end of this file.

An experiment corresponds to a folder containing scripts.
These scripts can do anything (e.g. numerical simulations, neural network training, etc.).

This folder must mandatorily contain three things:

- A subfolder called `config`. All configuration files required by the experiments will be saved here. For now, only `toml` and `json` formats are accepted.
- An `experiment_description` file (either `.txt` or `.md`) holding a complete description of the experiment, its purpose, and what it wants to achieve.
- A script called `run.py` that starts the experiment. For now it can only be a Python file.
  - This Python file must have a `run` function that returns a numeric value (the metric that `autoresearch` must optimize).
  - When the `run` command is implemented, `autoresearch` will execute precisely this `run` file.

# `add` Command

The `add` command will have the following flags:

- `--path_folder` : path to a valid config file. This flag is mandatory (already implemented).
- `--experiment_name` : name under which to save the experiment. If not specified, the name of the folder containing the experiment files is used (already implemented).
- `--metric_name` : name of the metric to optimize (new flag, mandatory).
- `--ascending` : specifies that the metric should be maximized. Cannot be passed together with `--descending` (new flag, mandatory).
- `--descending` : specifies that the metric should be minimized. Cannot be passed together with `--ascending` (new flag, mandatory).

Alternatively, a single flag called `--experiment_info_path` can be passed, containing the path to a `json` or `toml` file that includes all the fields listed above.
It goes without saying that if `--experiment_info_path` is provided, no other flag can be passed.

Once the path to the experiment files has been received, the following checks must be performed:

- That the path is valid and the folder exists.
- That the `config` subfolder is present.
- That an `experiment_description` file (`.txt` or `.md`) is present. If no such file is found, raise an error.
- That the `run.py` script is present:
  - That it contains a `run` function.
  - That the `run` function returns a value:
    - Use AST (Abstract Syntax Tree) to verify this — an example is provided below.
    - If there is no return statement, raise an error.
  - If there is a return value, check via annotation that it is a numeric type (another example is provided below):
    - If the check succeeds and the return type is numeric, proceed.
    - If it is not numeric, raise an error.
    - If there are no annotations, let it pass but generate a warning stating that it was not possible to verify the return type of the function and that the user must ensure it is a numeric value.

Once all checks have passed, create a folder called `jlt_log_<experiment_name>` where all logs automatically generated by `autoresearch` will be saved in the future.
`<experiment_name>` refers to the experiment name specified by the `--experiment_name` flag.

Also add a file called `summary_log.md` that will eventually contain a summary of all experiments carried out.
Since at the time of creation no experiment has been run yet, simply write "No experiment has been executed yet" inside it.

Add a simple readme (in `.txt` or `.md`) inside the folder explaining its purpose.

## Check Return Value — AST

The following is an example only. If you have a more elegant solution, feel free to implement it.

```python
import ast
import inspect
import textwrap

def has_return_value(func):
    source = textwrap.dedent(inspect.getsource(func))
    tree = ast.parse(source)

    for node in ast.walk(tree):
        if isinstance(node, ast.Return) and node.value is not None:
            return True
    return False
```

---

## Check Return Value — Through Annotation

The following is an example only. If you have a more elegant solution, feel free to implement it.

```python
import inspect

def get_return_annotation(func):
    sig = inspect.signature(func)
    return sig.return_annotation is not inspect.Parameter.empty
```

# `list` and `remove` Commands

These commands are fairly self-explanatory.

`list` displays all experiments saved in the registry.

`remove` removes an experiment from the registry. Note: it only removes the experiment from the registry; it does not physically delete the folder.

# Registry Behaviour

*(This is still provisional and may change as work progresses.)*

The registry must keep track of where experiments are located and of the results obtained.

For each experiment, the numeric value of the metric after each `round` must be saved in both a `csv` file and a `txt` file.
Example with the `txt` file:

```txt
1, 0.4532
2, 0.4766
3, 0.5811
4, 0.6101
```

For each round, a `log` file will also be produced containing observations about the experiment and the optimisation process.
Files will be named `round_i.md`, where `i` is replaced by the round number.
These files do not need to be implemented now (they will be added later when we work on the `run` command implementation), but it is important to be aware they exist.

In addition to the per-round log files, there will also be a summary log file per day (`summary_log.md`) that will be updated at the end of each experiment.

All this information must be saved in:

- The `jlt_log_<experiment_name>` folder (next to the experiment folder).
- A folder internal to the tool named `<experiment_name>`.

The rationale behind this duplication is to maintain a backup inside the tool in case the experiment folder is lost, deleted, etc. — and conversely, if something happens to the tool's internal folders, a copy will still be available inside the experiment folder.
